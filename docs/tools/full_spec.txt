1. Project Vision and Scope
SmartPark AI is a mobile-first parking management system designed for small parking facilities. The
owner uses an Android phone to capture a vehicle number plate at entry and exit. The app records
timestamps, calculates the fee from configurable tariff rules, and maintains a searchable history.
Core workflow
 Entry: Capture a plate image, recognize text, let the owner confirm/correct the registration, then
create an active parking session.
 Tracking: Store the entry timestamp and show the vehicle in the active parking list.
 Exit: Scan or search the same registration, find the active session, capture exit time and calculate
duration and fee.
 Payment and receipt: Record payment status and provide a receipt with entry, exit, duration
and amount.
 Dashboard: Show active vehicles, today's entries/exits, daily collection and parking history.
Project objective
Create a practical, offline-capable Android application that reduces manual recordkeeping and arithmetic
errors. Describe it as an AI-assisted system; do not claim perfect recognition or fully autonomous
operation.

5. Billing Rules and Worked Example
Choose a tariff policy and state it clearly in the app and report. Example policy: ₹30 for the first
started hour and ₹20 for every additional started hour. Under this example, a stay of 2 hours 25
minutes costs ₹70.
For duration D in minutes:
 Charge = 30 + ceil( max(0, D − 60) / 60 ) × 20

Billing edge cases to test
 Stay under the configured grace period.
 Exactly one hour, one hour plus one minute, and exactly two hours.
 Overnight parking across midnight.
 Missing active session at exit.
 Duplicate entry and repeated exit tap.
 Tariff settings changed after a completed transaction.
6. Camera and OCR Design
ML Kit Text Recognition extracts text from an image; it is not a dedicated Indian vehicle plate
detector. For the MVP, use camera capture, image cropping if practical, OCR, normalization and
manual confirmation. Avoid claiming perfect recognition.
 Normalize candidate text to uppercase and remove irrelevant spaces/hyphens according to your
chosen plate format.
 Use format checks as a warning, not an infallible rejection rule; special registrations may differ.
 If OCR is uncertain or finds no usable text, allow manual entry or a retake.
 Test outdoors and indoors, with angled plates, glare, blur and low light.
 Do not create a session until the operator confirms the plate.

PROJECT
SmartPark AI — Mobile-First Smart Parking Management System. Act as a senior Flutter
developer, Android engineer, database architect, UI/UX designer and testing engineer. Build a
functional Android app for small parking owners in India. The MVP must be demonstrable within
seven days.
TECH STACK
- Flutter and Dart.
- SQLite using Drift or a maintained compatible package.
- Camera capture for vehicle number plates.
- Google ML Kit Text Recognition for OCR.
- Local-first operation; no mandatory cloud backend, paid API or login for core operations.
- Modular UI, database, OCR and billing code.
SCREENS
1. Dashboard: today's revenue, active vehicles, entries, exits and occupancy.
2. Vehicle Entry: camera capture, OCR, editable registration, category and confirmation.
3. Vehicle Exit: scan/search plate, active session, duration, bill and exit confirmation.
4. Active Parking: searchable parked-vehicle list.
5. History: completed sessions, dates, amounts and payment status.
6. Tariff Settings: first-hour rate, additional-hour rate, grace period and rounding policy.
7. Reports: daily totals and CSV export.
8. Receipt: plate, entry/exit timestamps, duration, tariff breakdown and final amount.
OCR REQUIREMENTS
Request camera permission; capture an image; run OCR; normalize the candidate; validate likely
registration formats without unnecessarily rejecting special registrations; allow manual
correction; show an error when no usable text is found. Never create a transaction
automatically from uncertain OCR. OCR is not dedicated plate detection, so keep this
limitation clear.
TRANSACTION LOGIC
At entry, store a timestamp and create an ACTIVE session. Prevent duplicate active sessions
for the same plate. At exit, find the active session, record exit timestamp, calculate
duration and fee from configured rules, show a breakdown, save the final amount and mark the
session COMPLETED. Prevent duplicate exit processing. Handle overnight parking and invalid
timestamps. Preserve completed amounts when tariffs change.
DATABASE
Create parking_sessions, tariff_settings and payments tables with primary keys, appropriate
foreign keys, constraints and indexes. Keep payment status separate from session status. Save
the tariff used for each completed transaction or an equivalent tariff snapshot.
QUALITY
Core features must work offline and persist across app restarts. Add loading states,
validation, permission-denial handling, empty states and error messages. Use real database
values, not hardcoded dashboard totals. Add tests for billing, duplicate entry, missing active
session, overnight parking and repeated exit.
DELIVERY
Work in stages: (1) inspect environment and create project, (2) UI/database, (3) billing, (4)
camera/OCR, (5) reports, (6) physical-device testing, (7) release APK. After each stage, run
relevant checks and report implemented features, incomplete items and errors. Do not claim
success without testing. Deliver Flutter source, working APK, README/build instructions,
database schema, architecture documentation, billing tests and known limitations. Prioritize a
reliable MVP over unnecessary complexity.

16. Database Schema (exact)
Enable foreign keys in onConfigure (PRAGMA foreign_keys = ON). Create everything in onCreate.
Two columns were added to Part A's design: category (entry screen) and capacity (dashboard
occupancy).
CREATE TABLE tariff_settings (
  id INTEGER PRIMARY KEY CHECK (id = 1),
  first_hour_rate INTEGER NOT NULL CHECK (first_hour_rate >= 0),
  additional_hour_rate INTEGER NOT NULL CHECK (additional_hour_rate >= 0),
  grace_minutes INTEGER NOT NULL CHECK (grace_minutes >= 0),
  rounding_rule TEXT NOT NULL CHECK (rounding_rule IN ('STARTED_HOUR','FULL_HOUR')),
  capacity INTEGER NOT NULL CHECK (capacity >= 1),

17. Business Rules (exact)
17.1 Duration and billing
durationMinutes(entryMs, exitMs):
  if exitMs < entryMs: throw InvalidTimestampException
  return (exitMs - entryMs) ~/ 60000 // integer division
calculateCharge(durationMinutes, tariff):
  if durationMinutes <= tariff.graceMinutes: return 0
  extra = max(0, durationMinutes - 60)
  hours = STARTED_HOUR ? (extra + 59) ~/ 60 // ceiling
                       : extra ~/ 60 // FULL_HOUR (floor)
  return tariff.firstHourRate + hours * tariff.additionalHourRate
The breakdown object holds: durationMinutes, graceApplied, firstHourCharge, additionalHours,
additionalHourRate, additionalCharge, total. When grace applies, every charge is 0. These vectors
(tariff 30 / 20 / grace 10) are mandatory tests:

17.2 Plate normalization and validation
 Normalize: uppercase, then remove every character that is not A–Z or 0–9. “hp 01 ab-1234”
becomes HP01AB1234.
 Hard rule (blocks saving): normalized length must be 4 to 12.
 Soft warning (never blocks): text does not match either pattern below; show “Unusual format,
please verify”.
 Standard: ^[A-Z]{2}[0-9]{1,2}[A-Z]{0,3}[0-9]{4}$. Bharat series:
^[0-9]{2}BH[0-9]{4}[A-Z]{1,2}$.
 Normalizer tests: ‘hp 01 ab 1234’ → HP01AB1234; ‘HP-01-AB-1234’ → HP01AB1234;
‘MH12.DE.1432’ → MH12DE1432; empty → empty. Validator: HP01AB1234, DL8CAB1234 and
22BH1234AA match; ABC fails the hard rule; KA01 passes the hard rule with a warning.
17.3 OCR candidate selection
1.  Run the recogniser on the captured file. Collect every text line, in block order.
 
2.  Build candidates: each line normalized, plus all lines joined and normalized (covers two-line
 plates). Drop candidates outside 4–12 characters.
3.  Search each candidate with the non-anchored standard and Bharat patterns; the first hit
 becomes the suggestion.
4.  If there is no pattern hit, use the longest remaining candidate that contains at least one letter
 and one digit.
5.  If nothing remains, show “No plate text found. Retake or type the number.” Always put the
 suggestion in an editable field and list up to 4 other candidates as tappable chips.
6.  Never save from OCR output alone; the operator must press Confirm. Do not auto-substitute
 look-alike characters (0/O, 1/I).
17.4 Entry, exit and payment transactions
 Entry: in one transaction insert an ACTIVE session with entry_time = now. A second ACTIVE
session for the same plate must fail with DuplicateActiveSessionException (enforced by
ux_active_plate and by a pre-check for a friendly message).
 Exit preview: find the single ACTIVE session by normalized plate. None found →
NoActiveSessionException. Capture exitMs once when the bill is generated and use that same
value on confirm.
 Exit confirm (one transaction): re-read the row; UPDATE ... WHERE id = ? AND status =
'ACTIVE' must affect exactly 1 row, otherwise throw AlreadyCompletedException (repeated tap
or double processing). Save exit_time, duration_minutes, amount, tariff_snapshot, status =
COMPLETED, then insert the payments row.
 Payment at exit: switch “Payment received” (default on) plus method chips Cash / UPI. On →
PAID with paid_at = now. Off → UNPAID, paid_at NULL. UNPAID sessions can later be marked PAID
from the Receipt screen (method chooser).
 Tariff change: updates the single tariff row only. Completed amounts never change. Active
sessions are billed with the tariff in force at exit.
 Dashboard maths: collection today = sum of PAID payments with paid_at today; entries today =
entry_time today; exits today = exit_time today; active = ACTIVE rows; occupancy = active /
